# CLAUDE.md — sellingsgproperty.com

Instructions for any Claude session working in this repo (Claude Code terminal, cloud sessions).

## The goal (every change is judged against this)

sellingsgproperty.com exists to get maximum exposure for Jack Leow (CEA R074023I, PropNex Realty Pte Ltd, L3008022J):

1. **Rank #1 on Google** for "new launch condo" searches and for specific condo names.
2. **Be found and linked by AI assistants** (ChatGPT, Gemini / AI Overviews, Perplexity, Claude, Copilot): AIO and GEO.
3. **Show trust**: accurate, sourced, dated facts; no hype; no fake-looking ratings or stock photos presented as real.
4. **Work well on mobile and desktop.**
5. **Load fast** (pass Core Web Vitals on mobile).

Work as a senior SEO / AIO / GEO / UX / UI specialist who understands how people click, and how wording and colour affect trust. Add proactive recommendations that serve the goal.

**If a requested feature or change conflicts with the goal, say so before building it**, explain the trade-off, and propose an alternative. Examples of conflicts: content that only appears after JavaScript runs, entry pop-ups/interstitials, heavy scripts or widgets, hotlinked third-party images, unverified or exaggerated claims, copied competitor text, blocking copy/right-click, anything that breaks a page's own URL/title/canonical.

## Condo analysis standard (mandatory)

`docs/ANALYSIS-STANDARD.md` is mandatory for every condo analysis page (new launch or resale). Read it in full, including its 25 Nov 2026 amendment (which replaced the 5% test), before writing or updating any analysis: verdict first (banner, price gauge, Jack's recommendation, key points; no price-path chart), buy-at and walk-away prices from the closest competitors (within 1 km first, same tenure, similar size, +5% for pre-2023 area rules, averages not medians), the potential gain after costs, the competitors' latest 6- and 12-month transactions (data/comp-tx.json from `node scripts/ura-comps.cjs`), land bids within 2 km, rail catalysts, market checks, district, exit buyers, Master Plan, scorecard, and its evidence rules. `docs/` is internal and never served (forced 404 in `_redirects`).

## How the site is built

- Hosting: GitHub `main` → Netlify (auto-deploy, publish dir `.`, no build command on Netlify).
- `index.html`: homepage single-page app (markup, pre-rendered cards, head). Its main script lives in `assets/app.js`, loaded with a plain `<script src>` at the same spot (one cached file shared by the homepage and its route copies). **Source of truth for projects** is the `const projects = [...]` array in `assets/app.js`.
- `data/articles.js`: **source of truth for Insights articles** (bodies are not in index.html any more).
- `scripts/build-pages.cjs`: generates the crawlable static pages **and the homepage CSS**. Run `npm install` once (Tailwind v3 CLI), then **run it after any change to `index.html`, `assets/app.js` (projects), articles or `assets/site.css`, and commit the output:**

  ```bash
  npm install                         # once per machine
  node scripts/build-pages.cjs        # or: npm run build. Optional: AS_OF=YYYY-MM-DD node scripts/build-pages.cjs
  ```

  It writes `project/<slug>/index.html`, `new-launch-condos/index.html`, `insights/<slug>/index.html`, `insights/index.html`, `404.html`, the pre-rendered SPA routes `about/`, `contact/`, `mortgage-calculator/`, `deep-analysis/arina-east-residences/` (copies of `index.html` with their own head; never edit those copies), `assets/home.css` (compiled Tailwind) plus its `?v=` hash, `sitemap.xml` and `llms.txt`. Inside `index.html` it refreshes the static project cards (only the 12 newest are pre-rendered; the grid shows 12 and a "Show all N projects" button adds the rest, for speed: keep it that way), the hero tracker panel, every `<!--BUILD:VAL:key-->` number and the `?v=` hashes of `assets/home.css` and `assets/app.js`; inside `assets/app.js` it refreshes the article metadata.
- Homepage styling: Tailwind classes in `index.html` and `assets/app.js`, compiled by `tailwind.config.cjs` + `input.css` into `assets/home.css`. **Never re-add the Tailwind CDN, Font Awesome CDN or Google Fonts links.** Tailwind `violet`/`indigo` classes are remapped to the brand navy/brass in `tailwind.config.cjs`. Icons are CSS masks in `input.css` (only the icons in use; to add one, add its Font Awesome Free SVG there). Fonts are self-hosted in `assets/fonts/`.
- Condo Analysis (`/condo-analysis/` and `/condo-analysis/<id>/`): source is `data/condo-analysis.html` (scoped CSS, markup, script with research data). The build splits it into `assets/condo-analysis.css` and `assets/condo-analysis.js` (with `?v=`), moves each standard analysis (the `STD` line) into its own file `assets/std/<id>.json` loaded only when that condo opens (with a preload link in that page's head; never put the full set back into the main script, it is about 1 MB), fills the upcoming and post-launch lists from the `projects` array (`BUILD:SITE-UP` marker), and writes one pre-rendered page per condo file so each analysis has its own address; the script then makes it interactive and navigates without reloads. Detailed land-bid files in `NL.U` are matched by `pid`; scored launch files in `NL.L` by name. Post-launch files never show unverified units-left figures from `app.js`. Research goes in dated batches: condos with real stock left get a scored file in `NL.L` (scores follow the written rules, every figure dated and sourced); condos that are sold out, nearly sold out or have no published count get a `VSTAT` record (`out`, `early` or plain) with date and sources. Every launched and completed condo also carries a score: post-launch and completed condos without a full file get an `XSCORE` record (same five rules; completed condos skip the sales-progress points of the exit rule). Distances come from OneMap with MOE, NEA and LTA data from data.gov.sg, cross-checked with a listing or news source. Completed condos get the same deep dive as The Panorama (`renderOther`): at a glance, year by year, actual deals, against the district, future buyers, calculators, nearby competitors and sources. Its extra data is `CX` (developer, lease, unit mix, buyer profile, record psf from EdgeProp project pages cross-checked with Stacked Homes; biggest profits and losses and latest 3-bed resales from EdgeProp's matched URA resales; OneMap schools, MRT and distances to every other completed condo and to new launches within 3.5 km). School checks must include the three P1-S4 schools (Catholic High, CHIJ St. Nicholas Girls', Maris Stella High), which MOE lists as mixed level. Selling, post-launch and upcoming files get At a glance, Nearby competitors (resale condos within 1 km with URA 12-month psf, every project in the tool within 3 km, nearby land sales with EdgeProp's breakeven) and Who is buying, from `data/nearby.json` (EdgeProp project pages, OneMap, data.gov.sg; land parcels without an address are marked approximate). `scripts/nearby.cjs` splits it into one small file per condo, `assets/near/<id>.json` (loaded when that file opens; never go back to one big file). Selling, post-launch and upcoming files list resale condos within 3 km instead of 1 km (`r3` in `data/nearby.json`: URA median psf for the past 12 months, 3-bedroom (90-130 sqm) psf change over the past year and 4 years, homes and completion year from EdgeProp). Refresh with `node scripts/ura-resale.cjs` before the build; it needs the URA access key in `URA_ACCESS_KEY` or `~/.ura_access_key` (never commit the key), caches homes in `data/resale-homes.json` and site points in `data/site-geo.json` (new projects are placed approximately: check them). Selling and post-launch files get the same 3 km table. Profitable / unprofitable resale shares come from EdgeProp via `node scripts/edgeprop-profit.mjs` (needs Chrome; cached with a date in `data/resale-profit.json`; reads new condos and refreshes the 100 oldest counts each run), then re-run ura-resale. EdgeProp blocks GitHub's machines, so the monthly workflow `.github/workflows/refresh-resale.yml` (3rd) refreshes URA prices only, and a launchd job on Jack's Mac (`~/Library/LaunchAgents/com.sellingsgproperty.profit.plist`, 4th at 11:07, runs `scripts/monthly-profit-mac.sh`, log `~/Library/Logs/sellingsgproperty-profit.log`) refreshes the profit counts, rebuilds and pushes. After adding a project, run that script by hand. Spot-check resale psf against Stacked Homes when refreshing. Floor plans (every completed and selling-now condo except 8@BT, which has no published plans): `data/floorplans.json` holds redrawn sketches plus a `sales` table per layout (units, sold, developer psf from Stacked Homes' new-launch directory; refresh with the build_cx/fp_add scratch scripts). AC ledges excluded from strata area under the 2023 rules are drawn as `xledge` and not counted; mark such plans `harm: true`. Stacked Homes slugs can differ from ours (robertson-opus, coastal-cabana-ec). Floor plans: `data/floorplans.json` holds redrawn sketches (rectangles traced from the developer's plan, never the plan image itself; the user chose sketches over copied plans for copyright and trust), features, pros and cons for the main layout of each bedroom type (most units where Stacked Homes gives counts, else the size that resells most on EdgeProp). `scripts/floorplans.cjs` (run by the build) draws `assets/fp/<id>-<bed>.svg` and `assets/fp/plans.json`, loaded only when a file opens, and scores each layout with fixed rules (start 4; +1 regular shape, dumbbell, closable kitchen, kitchen or yard window, ledges under 5% (−1 at 10%+), store/shelter/utility; −1 long corridor, balcony over 12%). Use the developer's stated balcony and AC ledge areas where the plan gives them. Completed condos also have a price history (`HIST`: yearly average psf from URA caveats via Stacked Homes, recent prices by unit type, rents) that drives their year-by-year profit section and a sixth score, price growth (average of a price band and a profit band: the share of resales over the past 10 years that made a profit, from EdgeProp's matched URA resales where they cover 10 years, otherwise 99.co's all-time count; both shown), which counts for 40% of their overall score; cross-check the latest two years with SGinsite's URA transactions. The monthly check flags any launched project without a score, so an upcoming project is scored as soon as it launches. When research corrects a figure, fix `assets/app.js` too (`availableUnits`, `avgPSF`). Keep project names identical to `assets/app.js`.

## Project data rules

- Tabs by launch year: `year` is `"2024"`, `"2025"`, `"2026"` (launched) or `"2027"` (upcoming). Each project needs `launchSort` (YYYYMM); upcoming ones also need `launchShort` (e.g. `"Q1 2027 (est.)"`).
- When a project launches: move it to the launch year, add the verified launch result (date, units sold, average psf, source) and remove estimates.
  Also update its hand-built page and any articles about it (dated `launch-update` note at the top of an article; keep the original analysis). When you change an article, set `updated: 'D Mon YYYY'` in `data/articles.js`; when you change a hand-built page, bump its JSON-LD `dateModified`. Both feed the sitemap `lastmod`.
  A GitHub Action (`.github/workflows/check-launches.yml`, 1st of each month) runs `node scripts/check-launches.cjs` and opens a "Launch data needs updating" issue when a project is past its launch month, lacks a launch result, or its hand-built page is stale.
- Government land sites that are not sold yet live in `const landSites = [...]` in `assets/app.js` (between the `BUILD:LAND-SITES` markers). They get the "Land sites (GLS)" tab, a section at `/new-launch-condos/#gls` and pages at `/land-sites/<slug>/`. When URA/HDB awards a site, delete it from `landSites` and add it to `projects` as Upcoming (developer, land price, award date, sources); add a 301 from its `/land-sites/<slug>/` URL to the new project page.
- Upcoming projects may carry `landCost`, `landDate` and `sources: [{t, u}]` (shown on the static page). Use `launchShort: "Not announced"` with a placeholder `launchSort` (e.g. 202812) when the developer has given no date, `totalUnits: null` when no unit count is published, and `tenure: "Not stated"` when unknown. Never use marketing-agent project names until the developer confirms them.
- `mall: true` marks a condo built into the same development as a shopping mall (shown under the "Integrated with mall" tab). Ground-floor shops or a nearby mall do not count. The unit-size tabs use `totalUnits`; projects with `totalUnits: null` appear in none of them.
- Upcoming projects: `startingPrice: null`, `avgPSF: null`, `unitMix: []`, `amenities: []` until the developer releases them. Mark market-report dates as "est.".
- Never reuse another project's image. No image → leave `image: ""` (upcoming cards show "Upcoming"). Prefer self-hosted WebP under ~200 KB.
- Verify facts against developer announcements, URA/HDB and reputable reports (EdgeProp, Business Times, Straits Times, Stacked, 99.co) before publishing. Projects re-verified line by line are listed in `VERIFIED_DETAIL` in the build script; only those show unit-mix tables on their static pages.

2. Spot-check one project page and one article on a narrow (390 px) viewport: no sideways scrolling.
3. Every page keeps a unique `<title>`, meta description, canonical and valid JSON-LD.
4. Double-check every new or changed fact (prices, psf, units sold or left, dates, land prices, distances, regions) against a second, independent source, preferably the developer's release, URA/HDB, EdgeProp, Business Times or Straits Times. Recheck the arithmetic (score workings, % gaps, sold %) and that `assets/app.js` agrees with the Condo Analysis data. If a fact has only one source or sources disagree, say so on the page and in your summary.
5. Mention any goal conflicts you noticed in your summary.
